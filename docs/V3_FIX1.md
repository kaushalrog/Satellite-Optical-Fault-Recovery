# Fix 1: horizon-boundary defect in the rate bound

**Found by:** the in-metric rate-certificate check added for v3 (`cert_rate_violation_fraction`) flagged 4 of 1,020 CLAC/GAT held-out runs (network_transfer, GAT and GAT-fixed, seeds 409 and 417): one sample each, at follower age exactly 3.00 s, exceeding the carried rate bound by 3.4e-4 and 5.9e-4 rad/s.
**Cause:** at age a == h (h = 3 s, the horizon cap) the controller already holds the target (`age >= horizon` gives zero target rate), but `isc_clac('bound')` still used the extrapolating branch (`a <= hor`) for the rate bound. Lemma 1 as typeset also left a = h ambiguous (rate 0 for a ≥ h but F(a) given for a < h and a > h). The attitude bound is continuous at h and was never affected.
**Fix:** `a <= hor` -> `a < hor` in `src/isc_clac.m`; the Lemma now defines F(a)=ω̄ for a ≥ h.
**Why earlier audits missed it:** the Monte-Carlo test drew continuous ages (equality has probability zero) and the v2 replay never had a follower age land exactly on the cap. The earlier statement "rate certificate PASS" in `audit_v2/AUDIT_REPORT.md` is therefore corrected by this note.
**Handling:** lock 1 (`results/v3/lock.json`) and its results are kept unchanged (tag `v3-lock1-heldout-prefix`). The full 3,400-run held-out evaluation was re-run with the corrected code on the same seeds into `results/v3_fix1/` under a second lock; the paper reports the corrected run and discloses lock 1.

**Effect of the fix (measured):** all 3,400 held-out runs of lock 1 and of the corrected run are identical in pair RMS and attempted packets (the bound only changed at one sample per affected run and did not alter a decision); rate violations 4 -> 0 of 1,020. Re-running the 560 v2 CLAC/CLAC-fixed trajectories with the fix changes exactly one (beam_mismatch, CLAC-fixed, seed 215: pair RMS 0.006817 -> 0.006809 rad, 0.1 %), and gives 0 attitude and 0 rate violations. The v2 results stay as published; the difference is immaterial.
